# AI 私有知识库生态演进方向

> 文档性质：跨项目宏观参考与演进约束
> 适用范围：当前 `go-web`、`mixin-search`、`py-agent/314` 及目标文档服务、文档检索服务、QQ 检索服务
> 当前状态：上位产品方向；按来源划分写入与检索服务的目标边界见 [ADR-017](./adr/017-source-owned-document-and-search-services.md)，实施入口见 [`CURRENT_IMPLEMENTATION_PLAN.md`](./planning/CURRENT_IMPLEMENTATION_PLAN.md)

## 1. 文档目的

本文用于统一现有项目与目标服务的长期产品方向、系统定位、数据边界和演进原则，避免独立迭代中形成职责重叠、数据归属不清或知识检索相互混淆。

本文只描述宏观约束，不规定具体接口字段、数据库表结构、Agent 工具定义、检索参数或部署命令。实现细节应在后续专项设计文档中确定。

当前 go-web 仍处于无生产数据、无仓库外稳定客户端的初创开发期。此期间允许重置本地数据并直接调整内部结构和接口；空库可重复启动与产品语义正确性必须保留，而版本升级、备份恢复、灰度和旧接口兼容在出现真实生产约束后再建设。当前决策见 [ADR-005](./adr/005-development-baseline-over-production-migration.md)。

## 2. 产品愿景

这些应用与服务共同演进为一个以 Markdown 为核心的私有知识管理生态：

- 用户通过 Web 管理、编辑、审核和维护知识资产；
- 用户通过 QQ Bot 获取、讨论、整理和分享知识；
- 系统分别保存正式文档与原始聊天记录，并为两者提供严格隔离的相关性检索能力；
- AI Agent 在权限允许的范围内理解对话意图、选择知识来源并组织回答；
- 按内容的事实来源建立独立检索服务，为正式文档和 QQ 原始内容提供解析、索引和检索支持。

各应用和服务保持明确的代码与运行时边界，通过稳定接口组成统一产品。是否拆分代码仓库不决定数据所有权。

仓库采用 monorepo 组织方式：可独立部署的应用归入 `apps/`，跨应用共享的协议等稳定资产归入 `packages/`，产品与架构文档归入 `docs/`，部署资源归入 `deployments/`。目录集中不改变各应用的运行时边界和数据所有权。

## 3. 系统定位

### 3.1 go-web：Web 与用户身份入口

go-web 负责文档管理界面、用户账号和 QQ 用户到 go-web 用户的身份绑定。它通过文档服务的业务接口创建、修改和读取正式文档。目标架构中，go-web 不直接读写正式文档、知识空间或成员关系的业务表。

Markdown 仍是主要的原生编辑格式；DOCX、PDF 等文件可以作为受管理的正式文档资产。Web 产品入口与文档事实的写入服务可以分开部署。

### 3.2 py-agent/314：QQ 来源与智能编排

py-agent/314 负责 QQ 私聊、群聊及事件接入，保存 QQ 原始消息、文件、会话和撤回事实，并向 QQ 检索服务提供来源变更。它负责当前 QQ 会话的渠道事实和 Agent 工作流。

从 QQ 整理出的内容需要成为正式知识时，py-agent 调用文档服务创建草稿并传入可追溯的来源标识。py-agent 不直接写正式文档表，也不因保存聊天而自动创建正式文档。

### 3.3 文档服务：正式文档与知识空间的事实源

独立文档服务负责正式文档的草稿、版本、审核、发布、删除与详情读取，并拥有知识空间、空间成员、群与空间绑定、来源关系及文档变更 Outbox。它提供业务用例接口，不提供通用 SQL 写入接口。空间与活动 owner 成员在同一事务中建立。

### 3.4 按来源划分的检索服务

文档检索服务只接收文档服务的正式文档变更，维护该来源的关键词和向量索引。QQ 检索服务只接收 QQ 原始内容变更，并在内部区分文件与聊天消息的模型、生命周期和索引。检索索引都是可重建的派生数据。

现有 mixin-search 的文档与聊天实现是服务拆分的代码和契约基线，不作为长期统一的业务检索进程。只有明确需要在一次请求中查询两个来源时才增加组合查询服务；该服务只合并带来源的结果，不拥有事实、索引或权限。当前 go-web BM25 属于既有实现，长期应归入文档检索服务。

## 4. 核心知识域

### 4.1 私人知识库

私人知识库面向单个用户，主要承载：

- 用户在 Web 中创建或上传的私人文档；
- 用户通过 Bot 私聊提交的知识材料；
- 从私人聊天或其他授权来源整理出的文档；
- 尚未共享给团队的个人知识资产。

每个用户应具有明确的默认私人空间。私人知识可以在授权条件下被临时用于群聊回答，也可以通过显式操作共享或复制到团队空间。

### 4.2 团队知识空间

团队知识空间面向具有共同上下文的一组用户，典型来源是一个 QQ 群或一个协作团队，主要承载：

- 团队共同维护的正式文档；
- 从群聊讨论中整理并确认的知识；
- 由成员主动共享或复制进入团队的私人知识；
- 团队约定、项目资料和持续演进的共同知识资产。

QQ 群与团队空间通过独立绑定关系关联，不应把 QQ 群标识直接固化为知识空间本身。一个用户可以拥有私人空间并加入多个团队空间。

### 4.3 聊天记录域

聊天记录是独立于文档的原始信息域，保存用户在 QQ 私聊和群聊中的实际交流过程。聊天记录表示“当时讨论了什么”，正式文档表示“经过整理或确认后形成了什么知识”。

聊天记录可以长期保存并支持相关性检索，但不因被保存或索引而自动成为正式文档。将聊天内容转化为文档属于一次明确的知识晋升过程。

## 5. 数据归属原则

目标架构的数据归属如下：

| 数据类型 | 事实或派生数据负责人 | 说明 |
| --- | --- | --- |
| 正式文档、版本、知识空间和成员关系 | 文档服务 | 唯一业务写入方，提供文档与资源权限用例 |
| 用户账号与 QQ 用户身份绑定 | go-web | 提供经认证的用户身份 |
| QQ 原始文件、会话、消息和撤回事实 | py-agent 的 QQ 数据模块 | 晋升为正式文档时调用文档服务 |
| 正式文档检索索引 | 文档检索服务 | 根据文档服务的变更生成，可重建 |
| QQ 原始内容检索索引 | QQ 检索服务 | 根据 QQ 来源变更生成，可重建 |

数据来源、内容类型和知识空间分别建模：来源决定事实维护方，内容类型决定生命周期与索引规则，知识空间决定资源访问范围。同一个知识空间可以包含不同来源的正式文档；QQ 原始内容不会因为与空间相关就自动成为正式文档。

这些服务可以共享 PostgreSQL 或 Qdrant 实例，但各自使用独立业务表或 schema、写入账号和索引集合。跨服务查看或操作通过业务接口完成，不直接读写其他服务的表。具体边界见 [ADR-017](./adr/017-source-owned-document-and-search-services.md)。

## 6. 文档与聊天检索隔离

文档和聊天记录必须采用两套独立的检索流程与独立集合，形成明确的逻辑硬隔离：

- 文档检索只处理已授权、可检索的文档版本；
- 聊天检索只处理已归档并允许索引的会话内容；
- 两类语料使用不同的数据模型、切分方式、权限过滤、生命周期和引用形式；
- 联合回答可以同时使用两类检索结果，但不得在底层将两类语料混为一个无法区分的结果集合；
- 任何返回结果都必须保留其语料类型、事实来源和时间或版本信息。

文档通常具有更高的正式性；聊天记录更适合表达历史讨论、近期变化和人物观点。当两者存在冲突时，系统应向用户呈现差异，而不是隐式将聊天内容覆盖为正式结论。

现有多语料控制面隔离的实现见 [ADR-014](./adr/014-per-corpus-control-plane-isolation.md)；目标服务所有权与按来源检索拆分见 [ADR-017](./adr/017-source-owned-document-and-search-services.md)。

### 6.1 BM25 能力拆分约束

当前 go-web 中的 BM25 全文搜索是已实现的产品能力。目标是将正式文档的关键词索引与查询实现归入文档检索服务，并与该来源的向量检索共同提供查询能力。QQ 原始内容的关键词检索则归 QQ 检索服务，继续按文件与聊天消息分别处理。

本项目尚无生产数据和仓库外稳定客户端，可以直接重建开发数据库与索引，不要求保留旧接口或旧索引。改造仍需保持文档搜索的用户可见语义，包括权限、活动版本、更新、回收和排序。完成后，go-web 不再维护独立的正式文档检索内核。正式文档事实始终由文档服务治理，检索服务只持有可重建的派生索引。

## 7. 知识流通原则

知识在私人空间、团队空间和聊天场景之间流通时，应区分三种行为：

1. **临时读取**：仅在当前回答中使用某个空间的知识，不改变文档归属；
2. **持续共享**：目标空间获得对原文档的持续访问能力，文档仍由原空间治理；
3. **复制或晋升**：在目标空间形成新的文档资产，并保留原始来源关系。

群聊属于公开交互场景。用户在群聊中主动发起知识查询，视为具有在当前群公开获得回答的意愿。是否使用私人、当前团队或其他授权团队的知识，由 Agent 根据对话语义决定；实际可访问范围始终由权限系统约束。

公开回答不等于将私人文档永久共享给团队。持续共享、复制或转移必须形成明确、可撤销、可追踪的知识流转记录。

用户在私聊中可以使用自己的私人知识，也可以访问其有权加入的团队空间。Bot 加入某个群并不自动意味着所有私聊用户都能访问该群对应的团队知识。

## 8. 权限与身份原则

py-agent 判断 QQ 身份在当前私聊或群聊中具有什么渠道权限；go-web 负责用户账号与 QQ 用户身份绑定；文档服务依据知识空间和成员事实判定正式文档的资源权限。最终可用范围必须同时满足渠道与资源权限。Model 可以提出检索目标，不能授予权限或扩大范围。

群聊与团队空间之间保持独立、可撤销的绑定关系，由拥有空间的文档服务管理。查询方在调用检索服务之前取得限定范围的授权；检索服务验证请求没有超过授权范围，不在每次查询时回调事实源。授权凭证的签发者和字段应随服务拆分更新，见 [ADR-017](./adr/017-source-owned-document-and-search-services.md)。

## 9. 生命周期与可撤销性

正式文档应具有版本化生命周期。新版本完成处理并验证前，旧的有效版本可以继续服务；只有符合发布条件的版本才能成为正式检索来源。

聊天记录的长期保存、聊天索引和聊天晋升为文档是三个独立过程：

- 保存聊天不代表允许语义检索；
- 允许聊天检索不代表形成正式文档；
- 形成正式文档需要独立的创建、审核和发布过程。

系统应提供误上传、错上传和上传后反悔所需的治理能力，包括撤销发布、移动空间、移入回收站、删除、撤销共享和索引移除。

删除知识库文档与撤回已经公开的聊天回答是不同操作。系统应记录知识曾经被共享或公开使用的关系，以便执行尽可能完整的撤销和清理。

## 10. AI 能力边界

AI Agent 的职责是理解用户意图、选择合适的知识域、组织工作流程并基于证据生成回答。权限校验、数据归属、索引过滤、删除传播和生命周期状态必须由确定性的应用逻辑保证。

py-agent 中的 LangGraph 承载有状态的 QQ 交互和 Agent 工作流；来源专属检索服务承载知识解析、索引和查询。检索服务不实现会话 Agent 或正式文档治理。

普通 Agent 回答不应自动进入正式知识库。Agent 生成内容进入知识库时，应具有明确来源，并接受与其他文档一致的治理过程，避免未经确认的模型输出持续污染后续知识检索。

## 11. 演进阶段

### 已完成的开发基线

阶段一与阶段二建立了 go-web 文档事实、PostgreSQL BM25、事务 Outbox、mixin-search 文档影子索引及多语料控制面。它们是当前代码和本地测试的历史事实，不表示按来源拆分的目标服务已经实现。过去的 KEEP_BM25 结论只描述当时的检索评测结果，不再决定新的服务所有权。

### 下一阶段：按来源拆分写入与检索服务

先定义每张业务表、每套索引、每个跨服务接口的唯一负责人；随后建立独立文档服务，将正式文档、知识空间和成员关系的写入与读取移入该服务，并使 go-web 只通过业务接口访问。再从现有 mixin-search 中提取文档检索与 QQ 检索的独立模块、进程和存储命名空间。QQ 原始内容由 py-agent 管理；晋升为正式文档时调用文档服务。

服务间调用方向和权限凭证同时定型。文档服务不依赖检索服务完成写入，检索服务不在查询时反向调用来源服务。共享数据库设施时仍按服务分表、分账号与分索引。

### 后续产品能力

完成服务边界后接通 QQ 身份与知识空间、QQ 原始内容索引、QQ 文档草稿提交及授权查询。跨来源组合查询仅在产品需要时增加；它不改变各来源的事实所有权。最后分别完善文档与 QQ 内容的评测、容量和运行治理。

具体实施顺序和验收只在 [当前实施计划](./planning/CURRENT_IMPLEMENTATION_PLAN.md) 维护。

## 12. 明确不采用的方向

- 将文档服务做成接受任意表名或 SQL 的通用数据库写入代理；
- 让 go-web 或 py-agent 绕过文档服务直接读写正式文档与空间业务表；
- 让文档检索服务与 QQ 检索服务长期共用一套需同时理解两种来源业务规则的核心状态；
- 让检索服务在每次查询时反向调用事实源取得正文或权限；
- 把数据来源、内容类型与知识空间视为同一个划分维度；
- 将 QQ 原始聊天或普通 Agent 回答自动变成正式文档；
- 让 Model 直接决定或扩大用户权限；
- 在出现实际跨来源查询需求之前建立拥有业务事实的组合查询服务。

## 13. 宏观验收标准

- 正式文档、知识空间和成员关系只有文档服务可以写入；QQ 原始事实只有 QQ 来源模块可以写入；
- 文档检索与 QQ 检索能够各自消费变更、重建索引和完成查询；
- 服务调用关系没有同步调用环，检索服务查询时不回调事实源；
- 共享 PostgreSQL、Qdrant 设施时，各服务仍只写自己的业务表和索引；
- QQ 内容晋升为正式文档必须经过文档服务，并保留来源标识；
- 私人和团队知识空间按确定性权限规则使用，Model 不能扩大授权；
- 检索结果保留内容类型、来源、时间或版本及引用依据；
- 从空的本项目开发数据可以重复建立并验证上述边界。

## 14. 后续文档关系

本文定义跨项目产品方向和长期边界。[ADR-017](./adr/017-source-owned-document-and-search-services.md)记录本次写入服务与按来源检索拆分的目标架构；[当前实施计划](./planning/CURRENT_IMPLEMENTATION_PLAN.md)维护后续任务和验收。已有 ADR 与阶段报告保留当时的实现、测试与决策背景；与目标所有权冲突的历史表述按 ADR-017 的明确替代关系理解。

现阶段没有生产数据或需保留的开发数据，因此实施中可在核对本项目目标后清理开发库并从空数据重建。旧数据迁移、灰度切换和旧接口兼容不属于当前任务。文档与代码中的完成状态必须由实际实现及测试证明；本指南不把目标架构写成已完成事实。
