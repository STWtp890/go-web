# AI 私有知识库生态演进方向

> 文档性质：跨项目宏观参考与演进约束
> 适用项目：`go-web`、`mixin-search`（前 `go-rag`）、`py-agent/314`
> 当前状态：上位目标与边界基线；当前实施入口见 [`CURRENT_IMPLEMENTATION_PLAN.md`](./planning/CURRENT_IMPLEMENTATION_PLAN.md)

## 1. 文档目的

本文用于统一三个项目的长期产品方向、系统定位、数据边界和演进原则，避免各项目在独立迭代中形成职责重叠、数据归属不清或知识检索相互混淆的问题。

本文只描述宏观约束，不规定具体接口字段、数据库表结构、Agent 工具定义、检索参数或部署命令。实现细节应在后续专项设计文档中确定。

当前 go-web 仍处于无生产数据、无仓库外稳定客户端的初创开发期。此期间允许重置本地数据并直接调整内部结构和接口；空库可重复启动与产品语义正确性必须保留，而版本升级、备份恢复、灰度和旧接口兼容在出现真实生产约束后再建设。当前决策见 [ADR-005](./adr/005-development-baseline-over-production-migration.md)。

## 2. 产品愿景

三个项目共同演进为一个以 Markdown 为核心的私有知识管理生态：

- 用户通过 Web 管理、编辑、审核和维护知识资产；
- 用户通过 QQ Bot 获取、讨论、整理和分享知识；
- 系统分别保存正式文档与原始聊天记录，并为两者提供严格隔离的相关性检索能力；
- AI Agent 在权限允许的范围内理解对话意图、选择知识来源并组织回答；
- RAG 服务作为内部知识处理能力，为文档和聊天记录提供解析、索引和检索支持。

三个项目保持独立工程和独立部署能力，通过稳定的服务边界组成统一产品，而不是合并为单体应用。

仓库采用 monorepo 组织方式：可独立部署的应用归入 `apps/`，跨应用共享的协议等稳定资产归入 `packages/`，产品与架构文档归入 `docs/`，部署资源归入 `deployments/`。目录集中不改变各应用的运行时边界和数据所有权。

## 3. 系统定位

### 3.1 go-web：文档知识资产中心

`go-web` 是产品主系统和正式文档的事实源，负责：

- Markdown 为核心的文档管理体验；
- 私人知识库与团队知识空间；
- 文档编辑、版本、审核、发布、归档与删除；
- 用户、空间成员关系和文档访问权限；
- 多格式原始文件的保存与统一管理；
- 文档来源、派生关系和知识流转记录；
- 为 `py-agent` 提供唯一的正式文档知识来源。

`go-web` 应当是 Markdown-first，而不是 Markdown-only。Markdown 是主要的原生编辑格式，DOCX、PDF 等文件可以作为受管理的知识资产，其内容解析和检索能力由 `mixin-search` 辅助完成。

当前由 `go-web` 实现的 BM25 全文搜索属于既有产品能力和效果基线。长期演进中，全文搜索的产品入口、用户体验和权限语义继续由 `go-web` 承担，但 BM25 的索引与检索实现应逐步归入 `mixin-search`，避免文档检索能力同时分散在两个系统中；当前开发阶段不要求保留历史数据库或 HTTP 接口形状。

### 3.2 py-agent/314：QQ 交互与智能编排中心

`py-agent/314` 是 QQ 生态入口和 Agent 行为中心，负责：

- QQ 私聊、群聊及相关事件接入；
- QQ 身份、会话上下文和渠道权限管理；
- 原始聊天记录的长期保存能力；
- 基于对话语义选择知识来源和检索范围；
- 知识问答、聊天整理、文档创建和知识分享等 Agent 流程；
- 将 QQ 中产生的有效内容提交到 `go-web`，形成可治理的文档草稿或正式知识。

`py-agent` 可以是知识的生产者和来源，但不是正式文档的事实源。Agent 生成或整理的内容进入正式知识库前，应进入 `go-web` 的文档生命周期。

### 3.3 mixin-search（前 go-rag）：知识处理与检索中心

`mixin-search` 是辅助性的内部微服务，负责：

- 多格式内容解析与标准化；
- 文档和聊天记录的切分、索引与相关性检索；
- 关键词检索、向量检索、结果融合与重排；
- 返回具有明确来源和定位信息的检索证据；
- 支持索引重建、版本切换和删除传播。

`mixin-search` 不拥有最终用户体系、正式文档生命周期或 QQ 会话业务。其索引属于派生数据，应能够从上游事实源重建。

`mixin-search` 应逐步承接当前位于 `go-web` 的 BM25 全文搜索能力，并将其与向量检索共同纳入统一的文档检索能力边界。这里的目标是迁移和集中检索实现，而不是取消 BM25；关键词检索仍是正式文档检索的重要组成部分。

## 4. 核心知识域

### 4.1 私人知识库

私人知识库面向单个用户，主要承载：

- 用户在 Web 中创建或上传的私人文档；
- 用户通过 Bot 私聊提交的知识材料；
- 从私人聊天或其他授权来源整理出的文档；
- 尚未共享给团队的个人知识资产。

每个用户应具有明确的默认私人空间。私人知识可以在授权条件下被临时用于群聊回答，也可以通过显式操作共享或复制到团队空间。

### 4.2 团队知识空间

团队知识空间面向具有共同上下文的一组用户，典型来源是一个 QQ 群或一个协作团队，主要承载：

- 团队共同维护的正式文档；
- 从群聊讨论中整理并确认的知识；
- 由成员主动共享或复制进入团队的私人知识；
- 团队约定、项目资料和持续演进的共同知识资产。

QQ 群与团队空间通过独立绑定关系关联，不应把 QQ 群标识直接固化为知识空间本身。一个用户可以拥有私人空间并加入多个团队空间。

### 4.3 聊天记录域

聊天记录是独立于文档的原始信息域，保存用户在 QQ 私聊和群聊中的实际交流过程。聊天记录表示“当时讨论了什么”，正式文档表示“经过整理或确认后形成了什么知识”。

聊天记录可以长期保存并支持相关性检索，但不因被保存或索引而自动成为正式文档。将聊天内容转化为文档属于一次明确的知识晋升过程。

## 5. 数据归属原则

三个系统的数据归属遵循以下约束：

| 数据类型 | 事实源 | 说明 |
|---|---|---|
| 正式文档、版本与文档权限 | `go-web` | 由文档生命周期统一治理 |
| QQ 会话、消息与聊天上下文 | `py-agent` | 由 QQ 生态和会话语义统一治理 |
| 文档与聊天的检索索引 | `mixin-search` | 派生数据，可重建，不承担业务所有权 |

允许三个项目共享数据库基础设施，但不应共同读写同一组业务表。各项目应保持清晰的数据所有权；跨系统查看或操作优先通过服务边界完成。

## 6. 文档与聊天检索隔离

文档和聊天记录必须采用两套独立的检索流程与独立集合，形成明确的逻辑硬隔离：

- 文档检索只处理已授权、可检索的文档版本；
- 聊天检索只处理已归档并允许索引的会话内容；
- 两类语料使用不同的数据模型、切分方式、权限过滤、生命周期和引用形式；
- 联合回答可以同时使用两类检索结果，但不得在底层将两类语料混为一个无法区分的结果集合；
- 任何返回结果都必须保留其语料类型、事实来源和时间或版本信息。

文档通常具有更高的正式性；聊天记录更适合表达历史讨论、近期变化和人物观点。当两者存在冲突时，系统应向用户呈现差异，而不是隐式将聊天内容覆盖为正式结论。

### 6.1 BM25 能力拆分约束

当前 `go-web` 中的 BM25 全文搜索长期应拆分到 `mixin-search`；在尚无生产数据和外部客户端的开发阶段，可以直接重建内部实现和接口，但不得丢失搜索产品语义：

- `go-web` 继续承担文档搜索产品入口和权限语义，但不要求当前开发接口保持历史路径或字段兼容；
- BM25 索引与查询实现长期归入 `mixin-search`，并与向量检索共同构成统一的文档检索能力；
- 现有 BM25 的 owner 隔离、活动版本、更新、回收和排序行为作为效果基线；历史表结构和接口形状不构成当前门禁；
- 拆分完成后，`go-web` 不再维护一套与 `mixin-search` 并行演进的独立文档检索内核；
- 文档 BM25 与聊天 BM25 继续遵守独立集合、独立流程和明确语料来源的隔离原则。

BM25 的拆分不改变数据所有权：正式文档仍由 `go-web` 治理，`mixin-search` 只持有可以重建的全文与向量索引。

## 7. 知识流通原则

知识在私人空间、团队空间和聊天场景之间流通时，应区分三种行为：

1. **临时读取**：仅在当前回答中使用某个空间的知识，不改变文档归属；
2. **持续共享**：目标空间获得对原文档的持续访问能力，文档仍由原空间治理；
3. **复制或晋升**：在目标空间形成新的文档资产，并保留原始来源关系。

群聊属于公开交互场景。用户在群聊中主动发起知识查询，视为具有在当前群公开获得回答的意愿。是否使用私人、当前团队或其他授权团队的知识，由 Agent 根据对话语义决定；实际可访问范围始终由权限系统约束。

公开回答不等于将私人文档永久共享给团队。持续共享、复制或转移必须形成明确、可撤销、可追踪的知识流转记录。

用户在私聊中可以使用自己的私人知识，也可以访问其有权加入的团队空间。Bot 加入某个群并不自动意味着所有私聊用户都能访问该群对应的团队知识。

## 8. 权限与身份原则

`py-agent` 与 `go-web` 保持各自的权限职责：

- `py-agent` 判断某个 QQ 身份在当前私聊或群聊中可以执行哪些行为；
- `go-web` 判断对应用户可以访问哪些空间和文档；
- 最终有效权限是渠道权限与知识资源权限的交集；
- Model 可以基于语义选择检索目标，但不能授予权限、扩大身份范围或绕过资源校验。

QQ 身份与 go-web 用户之间需要具有可管理、可撤销的绑定关系。群聊与团队知识空间之间也需要独立绑定，以支持成员变化、空间迁移和未来的多渠道接入。

## 9. 生命周期与可撤销性

正式文档应具有版本化生命周期。新版本完成处理并验证前，旧的有效版本可以继续服务；只有符合发布条件的版本才能成为正式检索来源。

聊天记录的长期保存、聊天索引和聊天晋升为文档是三个独立过程：

- 保存聊天不代表允许语义检索；
- 允许聊天检索不代表形成正式文档；
- 形成正式文档需要独立的创建、审核和发布过程。

系统应提供误上传、错上传和上传后反悔所需的治理能力，包括撤销发布、移动空间、移入回收站、删除、撤销共享和索引移除。

删除知识库文档与撤回已经公开的聊天回答是不同操作。系统应记录知识曾经被共享或公开使用的关系，以便执行尽可能完整的撤销和清理。

## 10. AI 能力边界

AI Agent 的职责是理解用户意图、选择合适的知识域、组织工作流程并基于证据生成回答。权限校验、数据归属、索引过滤、删除传播和生命周期状态必须由确定性的应用逻辑保证。

`py-agent` 中的 LangGraph 主要承载有状态的用户交互和 Agent 工作流；`mixin-search` 中的 Eino 主要承载知识解析、检索和处理流程。两者不应重复建设相互竞争的会话 Agent 或文档治理逻辑。

普通 Agent 回答不应自动进入正式知识库。Agent 生成内容进入知识库时，应具有明确来源，并接受与其他文档一致的治理过程，避免未经确认的模型输出持续污染后续知识检索。

## 11. 演进阶段

### 阶段一：现状审计与边界固化

- 核对三个项目的现有模块、数据模型、接口、测试和部署方式；
- 识别重复能力、隐式耦合和缺失边界；
- 固化文档、聊天、索引、身份和空间的归属关系；
- 形成后续领域设计和服务契约文档。

### 阶段二：文档知识链路贯通

- 使 `go-web` 成为正式文档事实源；
- 建立文档版本、发布、删除与索引状态的一致链路；
- 将 `go-rag` 收敛为 monorepo 内独立部署的 `mixin-search`，只承担可重建的文档处理与检索能力；
- 以 `go-web` 现有 BM25 全文搜索作为正式读取与效果基线，通过可靠投递建立混合检索影子索引；
- 先完成持久化控制状态、真实存储授权过滤、重试重放、状态对账和影子评估，再讨论受控切换检索读取方；
- 在保持 Web 搜索产品语义清晰的前提下，形成统一的文档检索入口。

当前进度：go-web 阶段 1 和阶段 2 的 P2.0-P2.5 已完成，已经贯通文档事实、BM25、可靠影子索引、异步影子查询与来源分层评估。P2.5 的七类基线质量和收敛后正确性通过，但当前检索仍使用 local-hash-v1 评估 embedding，书面结论为 KEEP_BM25；正式搜索继续由 PostgreSQL BM25 提供。阶段 2 已收口，文档 BM25 的正式交接属于独立的 B 线工作，不阻塞后续阶段。

### 阶段三：QQ 身份与知识空间融合

- 建立 QQ 身份与 go-web 用户的绑定；
- 建立私聊与私人空间、群聊与团队空间的映射；
- 贯通 QQ 场景下的文档查询、文档创建和知识分享；
- 保证渠道权限与文档权限共同生效。

阶段三需要先完成**多语料检索基础设计**，但不必提前完成整个聊天产品域：聊天的长期保存、采集、Web 查看和知识晋升仍属于阶段四；而聊天语料契约、独立集合与权限边界必须在 `py-agent` 成为 `mixin-search` 的正式消费者之前确定。这样既不打乱宏观阶段顺序，也满足接入的安全前置条件。

`py-agent` 是 `mixin-search` 的第一个正式在线消费者，因此也是关键路径转折点：接入后 `mixin-search` 立即成为 QQ 知识问答的关键依赖，即使 `go-web` 仍使用本地 BM25。接入前必须完成调用身份认证、授权范围 capability、在线并发模型与不中断重建能力，完整门禁见 [ADR-012](./adr/012-multi-consumer-search-boundary-and-critical-path-shift.md)。

### 阶段四：聊天记录域建设

- 建立原始聊天记录的长期保存和管理能力；
- 建立独立于文档的聊天索引与检索流程；
- 支持 Web 统一查看聊天记录；
- 支持从聊天讨论到正式文档的知识晋升。

### 阶段五：治理、可靠性与持续演进

- 完善撤销、删除、回收站、索引重建和来源追踪；
- 建立文档与聊天检索的独立评测体系；
- 完善监控、审计、容量和故障恢复能力；
- 根据真实使用数据调整知识空间、分享和 Agent 交互体验。

## 12. 明确不采用的方向

在没有新的产品决策前，以下方向不应成为演进目标：

- 将三个项目强行合并为一个单体仓库或单体进程；
- 让 `mixin-search` 承担最终用户、团队空间或正式文档治理；
- 让 `py-agent` 绕过 `go-web` 成为第二个正式文档事实源；
- 将文档与聊天记录混入同一个无法区分的索引集合；
- 让 Model 直接决定或扩大用户权限；
- 将普通 Agent 回答自动回灌为正式知识；
- 在基础闭环形成前优先建设复杂的通用 SaaS、多集群或多渠道平台能力；
- 为非 Markdown 格式过早建设完整的在线编辑能力。

## 13. 宏观验收标准

每个阶段的具体测试标准由后续实施文档定义，但整体演进结果至少应满足：

- 三个项目的产品职责和数据所有权没有重叠冲突；
- 私人知识库与团队知识空间能够共存并受明确权限约束；
- 文档与聊天记录能够独立保存、索引、检索和删除；
- QQ 用户可以在授权范围内双向使用私人和团队知识；
- 群聊公开回答、长期共享和文档复制具有不同且可理解的语义；
- 从聊天整理出的文档能够追溯到原始来源；
- 正式文档更新和删除能够传播到检索系统；
- 检索结果能够区分正式文档与历史聊天，并保留引用依据；
- 任一项目可以独立演进，同时不破坏共同的产品边界。

## 14. 后续文档关系

本文是三个项目共同遵循的上位约束。后续应在完成代码级现状审计后，分别形成：

- 领域模型与数据归属设计；
- 身份绑定与权限模型；
- 文档处理和聊天处理流程设计；
- 跨服务契约与一致性方案；
- 分阶段实施与验收计划。
