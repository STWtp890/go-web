# ADR-017：按数据来源划分文档写入与检索服务

> 状态：已接受（目标架构，实施中）
> 日期：2026-09-25
> 修订：v2（2026-09-26，按责任划分修订：文档服务持有自己的资源访问主体，Web 与 QQ 身份不要求互相绑定，QQ 群绑定进入文档服务，两个检索服务各自独立消费）
> 适用范围：`go-web`、文档服务、文档检索服务、`py-agent` 与 QQ 检索服务
> 当前实施顺序：[CURRENT_IMPLEMENTATION_PLAN.md](../planning/CURRENT_IMPLEMENTATION_PLAN.md) §0
> 契约：[DOCUMENT_SERVICE_V1_CONTRACT.md](../contracts/DOCUMENT_SERVICE_V1_CONTRACT.md)、[SERVICE_IDENTITY_AND_CAPABILITY.md](../contracts/SERVICE_IDENTITY_AND_CAPABILITY.md)

## 背景

现有实现将正式文档写入、知识空间和用户功能放在 `gin-backend`，并将文档与聊天检索放在同一个 `mixin-search` 进程。随着 QQ 原始文件、聊天记录和从 QQ 整理出的正式文档加入，同一改动可能同时触及来源系统、文档领域、索引控制状态和查询接口。若检索服务在查询时再回调来源系统，就会增加同步调用依赖，难以独立修改和测试。

当前项目仍处于开发阶段，没有上线流量，也没有需要保留的数据。目标架构可从空的开发数据库和索引建立，不以旧表迁移、双写、灰度切换或旧接口兼容为前提。历史阶段报告只记录当时完成的实现，不代表本 ADR 的目标已经落地。

## 责任划分（v2 固定）

| 边界 | 唯一负责人 | 不负责 |
| --- | --- | --- |
| Web 界面、Web 账号、Web 侧业务入口 | `go-web` | 正式文档、空间、成员、群空间绑定、资源权限、文档业务表读写 |
| QQ Bot 身份命名空间、QQ 用户与群的会话事实、渠道权限、QQ 原始消息/文件/撤回事实 | `py-agent` 的 QQ 数据模块 | 正式文档、空间成员、资源权限判定、文档库写凭据 |
| 正式文档与版本、知识空间、成员、群空间绑定、资源权限、审计、文档 Outbox、文档详情读取、**资源访问主体登记** | 文档服务 | QQ 渠道权限、检索索引、Web 账号 |
| 正式文档索引与检索 | 文档检索服务 | QQ 原始内容、事实源查询时回调 |
| QQ 原始文件与聊天消息索引与检索（分别建模） | QQ 检索服务 | 正式文档、资源权限、渠道权限判定 |

## 决策

### 1. 正式文档由独立文档领域服务拥有

建立可独立运行的文档服务。它不是接受表名或 SQL 的通用数据库写入代理，而是正式文档的唯一业务写入方，提供创建、修改草稿、发布、撤销、归档、删除、读取详情和状态等用例。

文档服务拥有正式文档、版本、生命周期、知识空间、空间成员、群与空间绑定、文档来源关系、审计、文档变更 Outbox，以及**自己的资源访问主体登记表**。空间与活动 owner 成员须在文档服务的一次事务中建立。

`go-web` 保留 Web 界面、Web 账号与 Web 侧业务入口；它通过文档服务接口操作正式文档，不直接读写文档服务的业务表，也不持有这些表的写凭据。`py-agent` 同样不持有文档数据库写凭据。

文档服务同时提供正式文档详情和状态读取接口。只拆写入、让其他应用继续直接读取其表，会使生命周期和权限规则继续分散，因此不采用。

### 2. 数据来源、内容类型与知识空间分别建模

| 维度 | 含义 | 示例 |
| --- | --- | --- |
| 数据来源 | 原始内容由谁产生和维护 | `go-web`、QQ Bot |
| 内容类型 | 内容采用什么生命周期与索引规则 | 正式文档、QQ 原始文件、QQ 聊天消息 |
| 知识空间 | 哪些主体在当前场景下可访问 | 私人空间、团队空间 |

`py-agent` 的 QQ 数据模块拥有原始消息、文件、会话及撤回事实。QQ 原始内容不因被保存或索引而成为正式文档。需要转为正式文档时，调用文档服务的提交用例，由文档服务创建文档并保存来源系统、Bot/会话命名空间、原始记录 ID 和派生关系；此后由正式文档的版本与发布规则管理，进入文档检索服务。来源 ID 用于幂等提交和来源追踪，不能替代文档 ID。

同一个知识空间可以包含不同来源的正式文档；来源字段不代替空间权限。QQ 原始内容有自己的访问规则，不因它和某个空间相关就自动成为该空间的正式文档。

QQ 原始文件与聊天消息在 QQ 检索服务内部使用**独立的数据模型、数据表和检索索引**，不共用一张表或一个 collection。

### 3. 文档服务持有自己的资源访问主体，Web 与 QQ 身份不要求互相绑定

文档服务拥有资源访问主体登记表 `document_service.access_subjects`：主体键是带命名空间的规范字符串，例如 `web:user:42`、`qq:user:10001/20002`。**文档服务的业务表不引用任何其他服务的用户表**；`knowledge_spaces`、`space_members`、`documents`、`document_versions`、`document_grants`、`space_audit_events` 一律以主体键为外键。

- Web 请求与 QQ 请求分别通过受信入口提供身份材料。受信入口只接受持有边界密钥的已登记调用方（`go-web`、`py-agent`、`document-service`、`spacectl`）使用服务身份断言签发的凭据。
- 调用方**只能声明自己命名空间内的主体**：`go-web` 只能声明 `web:*`，`py-agent` 只能声明 `qq:*`。跨命名空间声明在校验阶段整体拒绝。
- 文档服务据此判定空间成员关系与文档权限。**两类身份不以互相绑定为前提**：QQ 主体可以是团队空间的活动成员而不存在对应 Web 账号；Web 主体也不需要先绑定 QQ 身份才能操作文档。
- 私聊/群聊等上下文由调用方在断言中提供，文档服务据此计算带标签的资源信封（决策 4）。
- 文档服务不签发自助身份，也不根据调用方的自称创建新的权限类别；主体的活动状态由文档服务自己的登记与空间事实决定。

**关于 QQ 与 Web 的绑定**：ADR-016 原方案把“QQ 身份 ↔ Web 用户绑定”作为私聊资源范围的来源。v2 取消了这一必需关系，理由是它把资源权限判定的输入放在另一个服务的事实上。QQ 主体对空间的访问一律来自文档服务自己的活动成员记录（显式授予），这与“入群不自动扩大资源权限”一致，而不是放宽它。

### 4. 资源范围解析属于文档服务，渠道权限属于 py-agent

```text
ResolveAccessScope(
    subject_key,            // 受信入口证明的主体：web:user:42 或 qq:user:10001/20002
    ConversationContext{    // 当前会话
        Kind:            Private | Group,
        ExternalGroupID: "...",   // 仅群聊
    },
) Resolution

Resolution = 判定二态 + 三类服务端标签
    Decision:      Granted | Denied{reason}
    Private:       []spaceID       // 该主体拥有的私人空间（0 或 1）
    CurrentTeam:   spaceID | none  // 群聊为当前群绑定的空间；私聊恒为 none
    OtherTeams:    []spaceID       // 该主体的其他活动团队空间
    member_space_ids: 服务端重算的并集（仅供调用方按标签裁剪，不作为输入）
```

- `Denied` 分支不携带任何范围字段，也不得降级为空 `Granted`：在文档契约里空范围等价于“仅 `authenticated_public`”，因此未获授权的主体不能取得公开文档、私人空间、团队空间或任何文档级范围。
- 三类标签只由文档服务生成、互不重叠：`CurrentTeam` 不得同时出现在 `OtherTeams`；私人空间不能成为 `CurrentTeam`（群绑定目标必须是 `team` 空间）。调用方不能提交或改写标签。
- **群聊判定**：`CurrentTeam` = 当前群的活动绑定空间，且该主体是它的活动成员；未绑定群 → `Denied{group_unbound}`；已撤销 → `Denied{group_binding_revoked}`；不是活动成员 → `Denied{not_space_member}`。其他群绑定的空间不得出现在 `CurrentTeam`。
- **私聊判定**：`Private` = 该主体拥有的私人空间（若已创建）；`CurrentTeam` 恒为 none；其他团队空间只以 `OtherTeams` 出现。主体不是任何空间成员时返回 `Granted` 且信封为空——这是“该会话目前没有可检索资源”，不是拒绝；只有主体本身未知或被停用才是 `Denied`。
- **渠道权限不在文档服务**：`py-agent` 提供 QQ 渠道结论（当前私聊/群聊允许的行为），调用方按标签裁剪文档服务给出的最大信封：`最大资源信封 ∩ 渠道策略 ∩ 调用方请求子集 = 最终范围`。文档服务不解释渠道策略，检索服务不解释任何一类权限。
- 多表读取使用单条 SQL / 一致性读事务，不得在并发改绑时拼出“旧绑定 + 新成员”这类混合快照。撤销在下一次解析与下一次签发立即生效，且不推进索引 generation、不切换 alias。

### 5. 检索按事实来源拆分，索引仍是派生数据

- **文档检索服务**只消费文档服务发出的正式文档变更事件，维护正式文档的关键词索引与向量集合，并提供正式文档查询；它不消费 QQ 原始内容。
- **QQ 检索服务**只消费 QQ 来源变更，维护 QQ 原始文件与聊天消息的索引；文件和消息在服务内部继续使用各自的数据模型、生命周期与索引集合，不共用 collection。
- `mixin-search` 现有文档与聊天实现是拆分时可复用的代码和契约基线，不作为两个来源长期共同修改的单一业务服务。
- 只有出现同一次请求同时查询两类来源的明确需求时，才建立组合查询服务。它只请求各检索服务并合并带来源的结果，不拥有原始内容、索引或权限事实。

文档服务在同一事务中提交业务变更和待投递事件；文档检索服务按自己的游标幂等消费，游标与索引状态在同一事务推进，因此崩溃只会导致重复投递，不会跳过事件。QQ 来源以相同原则向 QQ 检索服务投递变更。索引可从各自事实源重新建立，重建过程不需要在查询时反向调用来源。

### 6. 共享设施，不共享业务表及写权限

各服务可以使用同一个 PostgreSQL 实例和 Qdrant 集群，但各有独立 schema、独立数据库账号、独立表、独立索引 collection 与 alias：

| 服务 | schema / 库 | 写账号 | 索引命名空间 |
| --- | --- | --- | --- |
| 文档服务 | `document_service` | `document_service_writer` | 无（文档服务不写索引） |
| 文档检索服务 | `document_search` | `document_search_writer` | Qdrant alias `go_web_document_v1`，storage domain `document-search:documents:v1` |
| QQ 检索服务 | `qq_search` | `qq_search_writer` | Qdrant alias `qq_source_messages_v1` / `qq_source_files_v1`，storage domain `qq-search:messages:v1` / `qq-search:files:v1` |

每组业务表只有所属服务持有写权限。唯一的跨 schema 权限是**只读、按列**授予文档检索服务读取文档服务 Outbox（`document_service.document_events`）的 `SELECT`；QQ 检索服务不读任何其他 schema，它通过网络从 `py-agent` 接收 QQ 来源事件。写入权限矩阵由 `deployments/postgresql/verify-service-isolation.ps1` 以服务角色实测。

共享实例仍是共同的设施故障范围，不等同于独立数据库部署。当前开发数据可以在核对本项目目标后清理并从空库初始化；实现本决策不增加生产数据迁移、备份恢复、灰度或旧索引兼容任务。

### 7. 禁止同步反向调用和直接跨库写入

```text
go-web / py-agent  ──业务命令──> 文档服务 ──变更事件──> 文档检索服务
go-web / py-agent  ──渠道+资源授权──> 查询调用方 ──已获授权的查询──> 对应检索服务
py-agent QQ 数据模块 ──变更事件──> QQ 检索服务
```

- 文档服务不调用检索服务来完成写入；写入结果不以检索服务当次可用为条件。
- 检索服务不在每次查询时回调文档服务、`go-web` 或 `py-agent` 取得正文和权限。
- 查询方先从有权判定该资源的服务取得限定范围的授权，再请求检索。正式文档的资源权限由文档服务依据其主体、空间与成员事实判定，并签发短时资源范围 capability；QQ 渠道事实由 `py-agent` 判定并签发渠道范围 capability。两个检索服务只用共享边界密钥离线校验 capability，不做自省调用。
- 范围判定是包含：请求范围必须是已授予范围的子集，出现任何未授予标识整体拒绝，不静默裁剪。
- 检索结果包含内容类型、来源系统、来源记录 ID、正式文档 ID（若已晋升）、版本或时间及引用位置。查询方需要完整正式文档时，直接调用文档服务的详情接口，不经由检索服务回调。

### 8. 调用方向与依赖由可执行检查固定

- 三个新服务各自是独立 Go module 与独立可运行进程，只通过 `packages/proto` 的版本化契约与 `packages/gen` 的生成代码协作，不导入其他应用的 `internal` 包，不共享 GORM 模型或 Repository 实现。
- `packages/gen/servicearch` 提供跨服务架构检查：禁止跨服务 module 导入、禁止跨服务业务表写入、禁止业务代码依赖组合根。三个服务各自在 `internal/architecture` 中运行它。
- 两个检索服务不在查询路径上导入事实源的任何 Go 包；它们与事实源之间只有事件契约和 capability 校验。

## 对已有决策的影响

- [ADR-002](./002-document-index-ownership.md) 中“索引只保存派生数据”及版本、撤销、幂等语义继续有效；“`go-web` 是正式文档与空间的长期唯一事实源”由本 ADR 更新为“文档服务是事实源”。
- [ADR-012](./012-multi-consumer-search-boundary-and-critical-path-shift.md) 中调用授权和禁止检索反向校验的原则继续有效；“文档与聊天检索最终集中在一个 `mixin-search` 内核”不再是目标。capability 的信封格式继续沿用，audience 改为按服务划分：`document-service`、`document-search`、`qq-search`。
- [ADR-016](./016-qq-identity-and-knowledge-space-mapping.md) 的下列语义继续有效并迁入文档服务：Bot 身份命名空间、`Granted`/`Denied` 二态、三类服务端范围标签、只允许缩小的包含规则、审计与“入群不自动成为空间成员”。由本 ADR 更新的是：资源访问主体登记、空间成员与群空间绑定、资源范围解析全部属于文档服务；`qq_user_bindings` 不再存在（QQ 资源权限来自显式空间成员，而不是与 Web 账号的绑定）；`spacectl` 与 `go-web` 通过文档服务接口写入，不再直接写表。
- [ADR-008](./008-document-index-transactional-outbox.md)、[ADR-009](./009-shadow-index-compose-and-health-boundary.md) 描述的“文档事务 Outbox + 独立 Worker/Admin + 影子索引 Compose”是旧 `public.*` 投影的实现方式，已随阶段 C 退场：事件仍在同一事务提交，但消费者改为 document-search 自己的游标与已应用事件日志，运维入口改为 `RebuildIndex` / `GetIndexStatus`。[ADR-010](./010-shadow-query-evaluation-gate.md) 的影子查询质量门禁随影子索引一并退场。这些 ADR 保留为历史决策记录，不代表当前实现。
- [ADR-011](./011-bounded-cache-runtime-and-revision-fencing.md) 的 revision fencing 原则继续有效；其中文档缓存分区的具体入口随文档读写路径迁出 `gin-backend` 而退场。
- 既有阶段完成记录和验证报告保持历史事实；新的目标不会把过去未实现的服务拆分写成已完成。

## 实施顺序与验收

1. 定义文档命令与详情读取、文档/QQ 来源事件、服务身份与权限凭证契约；列出每张表、每个索引、每条事件和每条调用边的唯一负责人。
2. 建立三个独立 Go module 与可运行进程、独立存储配置、数据库账号与索引命名空间；`go.work`、`packages/proto`、`packages/gen`、根 Compose 由协作主线统一维护。
3. 文档服务实现正式文档与空间的写入、详情读取、事务约束、审计、Outbox 与资源范围解析；`go-web` 改为调用接口，并移除直接读写这些表的路径。
4. 文档检索服务与 QQ 检索服务分别只消费对应来源的变更，各自独立重建；QQ 原始内容晋升为正式文档时只调用文档服务，保留来源关系。
5. 仅在需要跨来源查询时新增组合查询接口，明确来源结果去重、排序和引用规则。
6. 从空的项目开发数据验证创建、版本、授权、撤销、重复事件、乱序事件、删除与索引重建；架构测试禁止跨服务私有包导入、跨服务业务表写入和同步反向调用。

完成标准是：正式文档和 QQ 原始内容各有唯一写入方；文档检索与 QQ 检索能各自建立和查询索引；服务调用方向可检查且没有同步调用环；共享数据库设施时各服务仍只写自己的业务表。上述标准由实际代码与测试证明，本文只记录目标决策。
