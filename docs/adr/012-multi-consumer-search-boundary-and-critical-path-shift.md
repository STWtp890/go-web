# ADR-012：多消费者检索边界与关键路径转变

> 状态：已接受
> 日期：2026-09-17
> 决策范围：阶段 3 起的多消费者接入，以及文档 BM25 的最终交接
> 输入评估：仓库根目录 [`MIXIN_SEARCH_SPLIT_ASSESSMENT.md`](../../MIXIN_SEARCH_SPLIT_ASSESSMENT.md)（外部架构评估，不属于 `docs/` 治理树）

## 背景

### 1. 拆分的完整因果链此前没有任何一处完整写出

指南与 [ADR-001](./001-search-service-boundary.md) 各自记录了这条链的一部分，因此“独立部署”看起来像架构偏好。完整链条是：

1. `py-agent` 必须经 RPC 检索知识库与聊天记录（指南 §3.2、§10）；
2. 聊天语料索引归 `mixin-search`（指南 §3.3、§6.1）；
3. 聊天 BM25 也在 `mixin-search`，不能落在 `py-agent`（消费者不持有检索内核）或 `go-web`（不拥有聊天）；
4. 文档 BM25 跟进，才能形成单一、可融合排序的检索内核（指南 §6.1、§3.3）；
5. `go-web` 因此不再维护并行检索内核（指南 §6.1）；
6. 所以“检索能力不分散”是**结论**，不是**前提**（指南 §3.1 的表述顺序掩盖了这一点）；
7. 检索因此必须可独立部署（ADR-001 背景只写了“需要”，未写“为何”）。

**支点是第 3 步**：一旦聊天检索落在 `mixin-search`，文档检索跟进才能形成统一检索内核。

### 2. 必要的限定

准确表述是：在「py-agent 需检索文档与聊天、聊天索引归 mixin-search、需要统一融合排序」这组既定约束下，独立检索服务接近结构性必需。

但「文档 BM25 必须物理迁入同一实现」**不是逻辑唯一解**。联邦检索（BM25 留在 `go-web`、向量检索在 `mixin-search`，由一方做跨服务融合）同样可行，代价是引入跨服务排序、权限过滤与故障组合复杂度，因此被拒绝。该替代方案被拒绝是因为代价，而不是因为不可行。

### 3. 接入前的代码实测（2026-09-17，提交 `c1f0b3b`）

| 项 | 实测事实 |
| --- | --- |
| gRPC 拦截器 | `cmd/rag-server/main.go` 使用 `grpc.NewServer(grpc.MaxRecvMsgSize(...))`，**没有 unary/stream interceptor** |
| TLS | 服务端无；两个内部 CLI 客户端使用 `insecure.NewCredentials()` |
| reflection | 已注册；能连上端口的调用方可直接枚举全部 API |
| 调用方身份概念 | 生产代码中 `caller`/`principal`/`tenant`/`audience` 均无实质命中 |
| `SearchDocuments` 授权 | `internal/rag/contract.go` 直接用请求中的 `AllowedSpaceIDs`/`AllowedDocumentIDs` 与文档访问快照做 OR 授权，**不校验调用方是否有权声明该范围** |
| 控制面并发 | 七个 RPC 全部在 `sync.RWMutex` 的**排他** `Lock()` 下先执行 `refreshControlStateLocked`（每次 `controlStore.Load()` 全量加载 + JSON 深拷贝） |
| 读路径网络 I/O | `SearchDocuments` 在持锁期间执行 `controlStore.Load()`、`SyncDocumentControls`（写 Qdrant）与补召回 dense/sparse 查询（读 Qdrant） |

**这是一个 capability confusion**：allow-list 被当作**授权输入**，而不是**待证明的授权主张**。任何持有网络访问权的调用方都可以自行扩大检索范围。

**今天不是漏洞**：唯一调用方是 `gin-backend` 的索引 Worker 与影子链路，allow-list 由事实源在自身权限校验之后产生，且根 Compose 只绑定 `127.0.0.1`。但“还没有第二个消费者”是时序事实，不是可依赖的安全属性。

## 决策

### 1. 保留拆分，并把两件事分别记录

- **决策 A（已由 ADR-001 作出）**：`mixin-search` 作为可独立部署的检索服务存在，由其消费者拓扑倒推而来；
- **决策 B（本 ADR 明确为后续目标）**：文档 BM25 的索引与查询实现最终迁入 `mixin-search`。

A 与 B 相关但不同。A 已经付出并保留；B 尚未发生，且不再被视为其他工作的前置条件。

### 2. 存在两个关键路径转折点，不是一个

```text
现在:  go-web ──异步投递/影子查询──> mixin-search
        fail-open · 最终一致 · 非关键路径

转折点一: py-agent ──正式知识检索──> mixin-search
转折点二: go-web Web 搜索 ──同步正式查询──> mixin-search
```

调用方向从未反转，改变的是**性质**：从「异步非关键依赖」变为「同步关键依赖」。因此正确表述是「异步非关键依赖 → 同步关键依赖」，而不是“运行时双向依赖”——后者会误导后续对循环依赖的判断。

**转折点一已经使 `mixin-search` 成为 QQ 知识问答的关键依赖**，即使 `go-web` 仍在使用本地 BM25。关键路径问题不能全部推迟到转折点二。两类消费者必须分别定义 SLO、超时、降级与容量隔离。

### 3. “可重建”只表示事实可恢复，不等于在线重建无中断

在此之前，重建 `mixin-search` 之所以安全，恰恰因为它还没有在线消费者。**这只对现状成立。** 一旦存在在线消费者，重建就必须走蓝绿路径：

```text
active index generation
      -> 后台构建 next generation
      -> 验证完整性、权限与质量
      -> 原子切换 collection alias
      -> 保留旧 generation 以支持快速回退
```

### 4. 首个在线消费者接入前的门禁

在 `py-agent` 成为正式消费者之前必须完成：

1. **调用身份认证**：区分 `go-web`、`py-agent` 与运维/开发调用方；
2. **范围 capability**：由 `go-web` 签发短时、限定 audience/用户/空间/文档范围的凭证，`mixin-search` 校验 `requested ⊆ granted`，**只允许缩小、不允许扩大**；
3. **索引写入权限与检索权限分离**，并按调用方、用户与会话记录审计与限流；
4. **控制面并发模型**：去掉每请求全量加载、全局排他锁与读路径内的投影同步；
5. **蓝绿重建能力**（见决策 3）；
6. **在线可靠性门禁**：并发索引写入下的 p50/p95/p99、错误率、吞吐、饱和点与限流。

**明确反对**“`mixin-search` 每次查询反向调用 `go-web` 校验”的实现方式：那会新增一条同步链路，与指南 §10 的确定性权限边界目标相矛盾，也把读路径的可用性绑定到第二个服务。

「只允许缩小」是可强制执行且可测试的：现有契约测试已覆盖 OR 授权，增加 subset 校验成本很低。

### 5. PostgreSQL BM25 是限时回退资产，不是永久双内核

`document_search_projection` 在交接初期必须保留，用于快速回退。回退路径不是伪二选一：

```text
保留 projection  <->  删除后失去降级能力
```

第三条主路径是「保留限时回退 + 蓝绿重建 + 明确退役条件」。

**退役门禁**（全部满足才删除 `go-web` 内部 BM25 内核）：

- `go-web` 正式读取已受控切换到 `mixin-search`，并具备自动回退与质量观测；
- 真实语义 embedding 与扩大后的标注评测集通过质量门禁；
- `mixin-search` 具备多实例、蓝绿重建与故障切换能力；
- 回退投影在观测窗口内未被触发，或触发后问题已修复并重新稳定。

### 6. 文档语料与聊天语料使用独立契约与独立集合

`mixin-search/v1` 的七个 RPC 全部是文档语义（`document_id`/`version_id`/`owner_space_id`/`lifecycle_revision`）。聊天消息、会话时间线、群身份、消息撤回与聊天归档**不能**通过增加一个 `corpus_type` 字段塞进同一套 RPC。

- 文档与聊天使用独立领域契约、独立集合、独立生命周期、独立删除与引用形式；
- 联合回答可以同时使用两类结果，但必须保留语料来源；
- `storage_domain` 来自控制存储 namespace，是**存储隔离**，**不是公开的语料类型契约**，不能替代聊天领域模型。

### 7. 授权语义的准确表述

`mixin-search` 当前完成的是**文档候选过滤**：它保证未授权、非活动、已删除的内容不会进入结果集，并执行事实源给定的访问快照。

调用方身份认证与授权范围证明**尚未建立**，是下一阶段门禁。因此在认证落地前，不得把“搜索结果正确”表述为“`mixin-search` 完成了最终调用授权”。

## 结果与权衡

- `mixin-search` 在转折点一之后不能再用“还没有消费者”解释其降级能力，蓝绿重建与 SLO 从理论问题变为排期问题；
- 增加调用身份与范围 capability 会在索引写入与检索两条路径上各引入一次校验，属于可信边界的最小代价；
- 保留限时回退投影意味着在一段时间内同时存在两套检索实现，这是刻意的过渡成本，而不是长期架构；
- 文档 BM25 的物理迁移被降级为可后置的独立工作线，不再阻塞 `py-agent` 接入。

## 验证

- `apps/mixin-search` 测试覆盖 `requested ⊆ granted` 的接受与拒绝，拒绝时不得扩大检索范围；
- 索引写入身份与检索身份的权限分离有独立测试，未认证调用失败关闭；
- 控制面并发改造后，查询延迟门禁必须覆盖并发索引写入状态，而不只是空闲状态下的功能正确性；
- 在线可靠性门禁使用扩大后的评测集，并同时报告 p50/p95/p99、错误率、吞吐与饱和点；
- 蓝绿重建按“构建 → 完整性验证 → alias 原子切换 → 旧 generation 回退”全流程验收；
- 上述门禁全部通过后，才允许 `py-agent` 成为正式在线消费者。

## 复审条件

出现以下任一条时，本 ADR 需要重新评估：

- `py-agent` 改为不依赖 `mixin-search`，或改为经 `go-web` 统一检索；
- 聊天语料检索被移出宏观阶段四范围；
- 检索质量长期无法超过 `go-web` 现有 BM25 基线；
- 蓝绿重建被证明无法在目标规模下满足恢复时间目标。
