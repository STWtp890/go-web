# ADR-016：QQ 身份与知识空间映射

> 状态：**草案，待评审**（评审通过后转为"已接受"，届时才据本 ADR 编码）
> 日期：2026-09-19
> 决策范围：P3.4（QQ 身份与知识空间映射）；P3.6 的接入前置
> 相关决策：[ADR-003](./003-chat-domain-boundary.md)、[ADR-012](./012-multi-consumer-search-boundary-and-critical-path-shift.md)、[ADR-014](./014-per-corpus-control-plane-isolation.md)、[ADR-015](./015-control-plane-idempotency-ledger-retention.md)；契约 [SERVICE_CALL_CAPABILITY.md](../contracts/SERVICE_CALL_CAPABILITY.md)、[CHAT_SEARCH_V1_CONTRACT.md](../contracts/CHAT_SEARCH_V1_CONTRACT.md)

## 背景

生态阶段三要建立 QQ 身份与知识空间的确定性映射（[生态指南](../ECOSYSTEM_EVOLUTION_GUIDE.md) §4、§8）。指南已经把职责划分写死：`py-agent` 判断某个 QQ 身份在当前私聊或群聊中可以执行哪些行为，`go-web` 判断对应用户可以访问哪些空间和文档，**最终有效权限是两者的交集**，且 Model 不能授予权限、扩大身份范围或绕过资源校验。

仓库现状是"地基已有、映射未建"：

- Phase 1 已建 `knowledge_spaces`（`private` / `team`）、`space_members`（含 `member_role` 与 `revoked_at` 软撤销）、数据库级不变量触发器 `validate_space_membership`（每个空间必须有活动 owner 成员；private 空间只允许该 owner），以及 `document_grants.grantee_space_id` 的跨空间授权建模；
- 但 `team` 空间**从未被任何代码使用**，成员表除 owner 行外没有写入路径，私人空间只在文档创建时惰性创建；
- **QQ 身份及其与 go-web 用户的绑定完全不存在**；
- 休眠的 `chat_groups` / `chat_group_members`（`deployments/postgresql/sql/service/chat/schema_init.sql`）属于**站内聊天产品域**，模块未注册路由，不是 QQ 群模型，不能当作现成的群身份使用。

要在动手前定下来的语义有三个：绑定关系的事实源与写入口、群与空间的关系基数、capability 换取入口的位置。三者一旦落进表结构与契约就具备跨系统契约性（capability 格式已有双端 golden vector 锁定），因此先决策后编码。

## 决策

### 1. 事实源与职责边界

- QQ 会话、消息、聊天上下文与**渠道权限**：`py-agent` 是事实源；
- go-web 用户、知识空间、空间成员、文档与**资源权限**：`go-web` 是事实源；
- **绑定关系（QQ 身份 ↔ go-web 用户、QQ 群 ↔ 团队空间）由 `go-web` 保存**：它是资源侧的身份映射，资源权限判定必须在 go-web 内闭合，不能依赖外部系统回传；
- `mixin-search` 继续不解释 QQ 身份（沿用 [ADR-014](./014-per-corpus-control-plane-isolation.md) 决策 5 与聊天契约 §2）：它只接收已经是空间/文档标识的 allow-list。

### 2. QQ 身份与用户绑定是可撤销的显式关系

- 同一 QQ 身份**至多有一条活动绑定**；同一 go-web 用户可以绑定多个 QQ 身份（为多渠道预留 `channel` 维度，本包只实现 `qq`）；
- 解绑与改绑都是**追加式操作**：写入新行或标记 `revoked_at`，历史绑定保留用于审计，不做物理删除；
- 解绑**立即生效**：判定读取活动绑定，不做任何索引侧补偿。

### 3. 私聊映射到该用户的私人空间

- 私聊的资源范围 = 绑定的 go-web 用户的 `private` 空间（复用 Phase 1 的惰性创建与触发器不变量，不新建第二套私人空间概念）；
- **未绑定的 QQ 身份没有任何资源范围**：不自动建账号、不默认可读公开文档。这是 fail closed：由 `py-agent` 引导绑定，而不是由 go-web 猜测身份。

### 4. QQ 群与团队空间：1 群 : 1 空间，可改绑，留审计

- 同一时刻：一个 QQ 群至多绑定一个 team space，一个 team space 至多被一个 QQ 群绑定；唯一性由数据库约束保证，而不是靠约定；
- 改绑 = 撤销旧绑定 + 新增活动绑定，保留完整历史（支持"空间迁移"与事故追溯）；
- team space 的 owner 是 go-web 用户（创建者），**群标识不进入空间主键**，避免把群固化为空间；同一个用户可以拥有私人空间并加入多个团队空间。

### 5. 群成员变化不自动扩大资源权限

- 空间成员是 **go-web 的事实**：群成员变化由 `py-agent` 影响**渠道权限**，从而在交集上收缩或保持不变；
- **不把"加入 QQ 群"自动同步为"成为空间成员"**：资源权限必须显式授予。否则任何能拉人入群的人都能间接扩大文档访问范围，与"渠道权限无法扩大资源权限"直接冲突；
- 反过来，把成员从空间移出**不**影响其渠道权限，但会立即从交集中消失。

### 6. 有效权限 = 渠道权限 ∩ 资源权限，求交在 go-web 闭合

- `py-agent` 提供：QQ 身份 + 该身份的渠道结论（当前私聊/群聊允许的行为）；
- `go-web` 计算资源侧：该用户可访问的空间集合与文档级条件（活动版本、`authenticated_public`、grants）；
- 有效范围是两者交集的**空间 allow-list**，并沿用既有的包含规则：请求范围必须是已授予范围的子集，出现任何未授予标识**整体拒绝**，不静默裁剪；
- 渠道权限不能扩大资源权限，资源权限不能绕过渠道限制，Model/编排层的输出不参与任何判定。

### 7. 撤销的生效路径是查询时求交，不是索引操作

- 解绑、移出空间、改绑、空间迁移都在 go-web 内即时生效；
- 生效路径是**查询时求交**（capability scope → 请求 allow-list → 候选级过滤），**不得用删除索引表达撤销**；
- 因此计划 §8 的验收"解绑或撤销后立即失去对应访问能力，不需要重建索引"由架构保证，并由测试断言（切换前后 generation 与 alias 不变）。

### 8. P3.4 交付确定性范围解析；capability 换取推迟到 P3.6

- P3.4 的交付物是**确定性函数** `ResolveSpaceAccess(userID) -> 活动空间集合`，输入只有 go-web 事实源中的行，同一输入必得同一输出（无时间依赖、无语义模型参与）；它同时是未来组装 capability scope 的唯一入口；
- **P3.4 不实现 capability 换取端点**：`py-agent` 如何以 QQ 身份换取短时 capability（含范围计算与审计字段）连同协议变更一起归入 P3.6，届时需要契约更新与双端 golden vector 的同步修改；
- 已知后果：在 P3.6 落地前，`py-agent` 无法通过本路径取得范围化 capability，P3.4 的范围解析只能由 go-web 内部与测试驱动验证。

### 数据结构草图（实现细节，待第 2 片定型）

| 对象 | 形态 | 关键约束 |
| --- | --- | --- |
| QQ 身份 | `qq_identities`（渠道 + 外部标识） | `(channel, external_id)` 唯一 |
| 用户绑定 | `qq_user_bindings`（身份、用户、`revoked_at`） | 每个身份至多一条活动绑定 |

## 结果与权衡

- **收益**：资源权限始终在 go-web 内闭合；QQ 侧变化不需要索引重建；绑定表带渠道维度，未来加渠道是加行而不是改模型；1 群 : 1 空间的约束把"空间迁移"变成一次可审计的改绑。
- **代价**：两套事实源必须在编排层求交，`py-agent` 必须传递渠道结论而不能只传 QQ 号；"入群不等于获得资源"需要显式授予，带来运营成本，这是用最小权限换来的。
- **明确不做**：capability 换取端点（P3.6）；聊天记录域、知识晋升与共享记录（阶段四）；多渠道适配器（只保留 `channel` 扩展点）；不把休眠的 `chat_groups` 当成 QQ 群模型；不新建第二套空间/成员体系。

## 验证：P3.4 的最低验收条件

1. 解绑或撤销后**立即**失去对应访问能力，且 generation 与 alias 不变（无索引重建）；
2. 群成员变化、空间迁移、群改绑三类事件都收敛到同一权限结果（同一输入同一输出，可重复断言）；
3. 反例成对存在：渠道声称可达但资源未授予 → 拒绝；资源已授予但渠道不允许 → 拒绝；
4. 未绑定的 QQ 身份在任何路径下都得不到非公开范围（fail closed）；
5. 编排层传入的空间集合超出解析结果 → 整体拒绝，不静默裁剪；
6. 群标识不作为知识空间主键；改绑后旧绑定仍可审计，且唯一性约束在并发写入下成立。

## 复审条件

- 出现同一自然人跨渠道（QQ 之外的渠道）统一身份的产品需求；
- 需要把群成员自动同步为空间成员（策略变更，需重新论证与最小权限的关系）；
- P3.6 的 capability 换取协议要求 go-web 暴露范围解析的其它形态（例如批量解析或预计算）；
- 出现跨 go-web 实例并发写入绑定的部署形态（需要分布式一致性讨论）。
