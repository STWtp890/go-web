# ADR-015：控制面幂等账本的保留窗口

> 状态：已接受，机制已实现（默认不清理，等待上限数值一并启用）
> 日期：2026-09-19
> 决策范围：P3.3 容量治理，实施于 `py-agent` 正式接入前
> 相关决策：[ADR-006](./006-mixin-search-control-state-commit-order.md)、[ADR-013](./013-immutable-control-snapshot-and-background-projection.md)、[ADR-014](./014-per-corpus-control-plane-isolation.md)

## 背景

控制面用一张幂等账本把每个已接受操作的响应记下来（文档语料是 `operations`，聊天语料是同名的 `operations` 字段）：

- 同一个 `operation_id` **重放**时返回首次响应，而不是重复执行；
- 同一个 `operation_id` 携带**不同载荷**时被拒绝（`ErrConflict`）。

账本是整份控制快照的一部分，因此每条记录都参与"整份复制 + 整份序列化 + 单行 CAS"，而且**只进不出**：

- 聊天语料是持续增长的高基数语料，账本条目数与写入次数同阶，**且每条记录携带该次请求的完整响应**——一次批量索引会把该批每条消息的状态都写进账本。容量实测（见实施计划 §7.1）表明，账本因此约等于把每条消息的负载再存一份：快照里"消息 + 账本"大致各占一半，它**不是可忽略项**，而是决定快照大小的两大部分之一；
- 写入代价由快照大小线性决定（50k 消息 ≈ 37.4 MiB、每次写入 ≈ 1.35 s）。账本把这份代价又抬高一份，且没有任何回收路径；
- 于是出现一个必须先回答的问题：**"重放保证"到底在多长时间内成立？** 不回答它，就只有两个坏选择——账本无界增长，或者清理掉消费者仍可能依赖的记录。

## 决策

### 1. 幂等保证是有窗口的，窗口必须写进契约

服务只承诺：在保留窗口内，重放同一 `operation_id` 返回首次响应，改绑不同载荷被拒。窗口之外不承诺"返回首次响应"。

窗口是契约的一部分，不是实现细节：生产者的重试与告警策略必须落在窗口内，窗口值写进聊天契约的容量一节，并在启动日志里打印实际生效值。

### 2. 窗口外仍然保证"不会重复写入"

这一点不依赖账本，因此清理不会破坏收敛性：

- 聊天的向量存储键由 `(storage domain, conversation_id, message_id, operation_id)` 决定，重放会重写**同一个键**，而摄取是整键替换，不会产生第二份向量；
- 消息内容不可变：已索引消息若携带不同内容，仍被状态本身拒绝（`ErrConflict`），与账本无关；
- 删除、归档、访问快照与撤回的幂等性同样由修订号与状态机保证（迟到修订被拒、重复修订不推进状态），账本只负责"返回首次响应"。

因此窗口之外**降级的是响应复现与改绑检测**，不是数据一致性。这一点已由实现时的测试固定：

- 窗口外、载荷相同：重放被接受，重写同一个向量键，不产生第二份向量，消息计数与修订不变；
- 窗口外、载荷不同：**如果这是该 `operation_id` 在窗口后的第一次到达**，会被当作新操作接受（改绑无从比较）；
- 一旦某个 `operation_id` 在窗口外被重新接受，它会被**重新记录**，此后改绑检测对该 id 恢复。

这一点必须在实现时逐条验证（见"验证"）。

### 3. 按年龄清理为主，条数上限兜底

- **年龄**（默认建议 **7 天**，`-chat-operation-retention`）：生产者的重试窗口由它自己的退避与告警策略决定，年龄是双方都能推理的量；
- **条数上限**（默认建议 **100,000 条**，`-chat-operation-max-entries`）：兜底，防止极端写入速率把快照撑爆；超限时按最旧优先清理；
- 两者是**任一先触发**的关系，因此**不存在"无条件保留 7 天"的承诺**：如果 7 天内写入的操作数超过条数上限，未满 7 天的记录会先被清掉。准确的契约表述是：**operation receipt 保留到"时间窗口"或"条数上限"任一条件先触发为止**；
- 因此条数上限不能随手填，应按峰值反推：

  ```text
  maxEntries >= 峰值操作数/天 × 保留天数 × 安全系数
  ```

  例如峰值 20,000 次写入/天、保留 7 天、安全系数 2 → 至少 280,000 条；填 100,000 条就等于把实际保证缩短到约 2.5 天（峰值下）。启用时必须同时核对这两个值，并把推导写进部署文档；
- 清理发生在**既有的机会式维护路径**（维护 pass 内、与待清理向量同批），不新增后台任务，也不引入新的并发面；
- 清理释放的空间必须能被容量守卫观察到：账本与消息共用同一份快照预算，守卫读的是持久化后的快照大小，因此清理后**下一次**写入即看到空间释放。

### 4. 本 ADR 定义窗口；机制已实现，数值与启用一并落地

清理机制已实现（配置项 `-chat-operation-retention`、`-chat-operation-max-entries`，默认 0 = 不清理，行为与今天一致），走既有维护路径。启用（填入数值）与容量上限数值一并落地，避免"先启用一个窗口、再改窗口"造成两次契约变更；默认建议值可以在启用时按实测调整。

## 结果与权衡

- **收益**：无界增长被消除；"重放保证多久"从隐含假设变成写下来的、可测的窗口；清理不引入新的后台任务与新的失败模式。
- **代价**：窗口外的重放会重新执行（对索引是幂等重写，对删除/归档是状态机幂等），并且**改绑检测在窗口外退化**——同一 `operation_id` 携带不同消息集在窗口外可能被当作新操作接受。这是明确接受的代价，必须写进契约，避免消费者以为幂等是永久的。
- **明确不做**：不把账本搬到独立表或按行存储。那是容量"迁移触发"命中后的事（见实施计划 §7.1），本 ADR 只负责把窗口定下来，使那之前的行为有界且可解释。

## 验证（实现时必须补齐）

已由实现补齐，逐条对应：

- 窗口内：重放同一载荷返回首次响应；改绑不同载荷被拒（`TestOperationIdReplayAndRebinding`）；
- 窗口外、载荷相同：不产生第二份向量，消息计数与修订不变（`TestOperationLedgerRetentionKeepsTheWindowAndForgetsBeyondIt`）；
- 窗口外、载荷不同：作为新操作接受，且不污染已有消息；重新接受后保护恢复（`TestOperationLedgerRebindingOutsideTheWindowIsAccepted`）；
- 清理只删过期条目，窗口内条目一条不动；条数上限触发时按最旧优先（`TestOperationLedgerCeilingDropsOldestFirst`、`TestOperationLedgerRetentionDisabledChangesNothing`）；
- 清理后容量守卫观察到快照变小（`TestOperationLedgerPruningFreesSnapshotSpace`）；
- PostgreSQL 上走真实 CAS 的清理（`TestCapacityGuardAgainstPostgres` 的 ledger retention 子测试）。

## 逐 RPC 的窗口外语义（实现已固定）

清理只影响"响应复现与改绑检测"，不影响业务幂等；每个 RPC 在窗口外的行为都被测试固定
（`TestExpiredLedgerReplayIsIdempotentPerRPC`，逐 RPC 子测试断言"语义状态与向量计数不变"）：

| RPC | 窗口外重放会发生什么 | 业务幂等由什么保证 |
| --- | --- | --- |
| `IndexConversationMessages` | 重新执行：同一条消息落到**同一个** deterministic 向量键并整键替换，不产生第二份向量；已索引消息的内容校验仍然拒绝改内容 | 向量键含 `operation_id` + 消息内容不可变 |
| `ArchiveConversation` | 重新执行：同一 `archive_revision` 再次写入同样的归档状态 | 归档修订号（低于当前修订即 `ErrStaleArchive`） |
| `UpdateConversationAccess` | 重新执行：同一 `access_revision` 再次写入同样的授权快照 | 访问修订号 + 快照是完整替换语义 |
| `RetractMessage` | 重新执行：同一 `retract_revision` 再次标记撤回 | 撤回修订号 |
| `DeleteConversation` | 命中该 `lifecycle_revision` 的删除结果缓存，直接返回墓碑结果，不触碰在线状态 | 墓碑修订号 + 删除结果缓存（`delete_results`） |

因此需要保留的"精简信息"是**修订号与墓碑本身**（它们是不可清理的权威状态），而账本条目只是响应缓存：清理它不会让任何 RPC 产生重复写入或状态漂移，代价仅是响应不再逐字复现、以及改绑检测在该 id 被再次接受前失效。

## 复审条件

- 出现必须在**无限期**内保证"同一 `operation_id` 必返回首次响应"的消费者（例如按 operation 对账的结算流程）；
- 实测证明账本清理会导致重复计费、重复可见或对账不一致；
- 控制面迁移到行级/分区存储后，窗口可以放宽甚至取消——那时本 ADR 的窗口语义应随 ADR-016 一并复审。
